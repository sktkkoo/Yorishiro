# 合意した目的と範囲で自走する作業

Status: experimental implementation（2026-10-26）

Yorishiro は、ユーザーと対話して継続的に任せる目的と対象範囲を決めた後、発話を待たずに次の仕事を判断して実行できる。ユーザーが目指すのは、一人で事業を進める時にも役割を任せられる相手であり、可逆なローカル作業の細かな許可を毎回求めない。画面では文書・開発のモードを選ばせず、目的と一つの対象フォルダ、許可するローカル操作からhostが実行方法を選ぶ。通常フォルダでは可逆なテキスト文書操作、Gitリポジトリのルートで全ローカル操作を許可した場合は隔離コピー内で文章やコードの変更・テストを行う。会社業務全体の自動化を提供するものではない。

## 委任と停止

- 初回は音声で相談する導線を主とする。現在の Codex Realtime 音声会話を再利用し、未接続ならユーザーの開始操作で接続する。文字での相談は Claude Code worker を使う代替経路であり、未入力でも AI から質問を始められる。
- 会話で決めた目的、フォルダ、操作、進め方、実行間隔、24時間の上限を AI が設定案にまとめる。`autonomy_propose` は案を保存するだけであり、権限を付与しない。
- 設定案は最初から編集可能な入力欄へ自動反映する。音声・文字の相談と手入力が同じ共有ドラフトを更新し、手で直した内容も次の相談に渡す。音声の開始・相談・案の作成だけでは自動作業を有効にしない。
- 設定画面の自動作業 On/Off は、保存済みの範囲だけを有効・無効にする。Off は現在の処理をキャンセルし、次回起動を止める。設定未完了なら On からセットアップを開く。
- 停止要求と終了確認を区別する。workerまたは相談処理の終了を待つ間は`stopping`として「作業プロセスの終了を待っています」と表示し、1秒ごとに確認する。新しい作業は開始しない。待機中に再度Onや範囲保存を行っても、以前の処理が終了するまで待つ。停止状態の保存に失敗した場合も、画面は実際のキャンセル状態を再取得する。
- 実行中の範囲変更・停止後に届いた古い worker の結果は適用しない。
- 能力不足や実行失敗では止まり、仕事がない時は変更を作らない。目的達成時の扱いは以下の進め方で分ける。

## 会話と手入力の共同編集

設定を開くと、目的、対象フォルダ、許可する操作、進め方、頻度、上限を編集できる。初回設定と会話から新しい案が届いた時は自動で開き、編集中に自動で閉じない。会話エージェントは相談の途中から `autonomy_propose` で同じ設定案を更新する。別のMarkdown文書をユーザーに転記させない。

共有ドラフトには単調増加する revision と更新ごとの ID を持たせ、native event で即時通知する。15秒の状態確認は取りこぼし回復用に残し、古い読取結果で新しい画面を巻き戻さない。手入力は500msの待ち時間でまとめ、IDが一致するときだけ差分を保存する。AI側も最新案を読み、IDを指定して更新する。文字相談は開始時のIDとrevisionを照合し、推論中に変わった入力を上書きしない。

ユーザーが編集中の欄は新しいAI案で置き換えない。別の欄の変更は反映し、同じ欄で競合した場合は自分の入力とAI案のどちらを使うか選べる。同期中・競合中は設定の確定を待つ。未完成の目的やフォルダ入力もドラフトとして保持し、実行権限の検査は最後の確定時に行う。共有ドラフトはアプリのプロセス内に保持し、アプリ終了後の復元は対象外。

## 継続して任せる範囲と今日の仕事

初回 UI の既定は「その日の仕事を先に相談」する `daily`。保存済みの旧設定で指定がない場合は従来の `automatic` として扱う。

- **daily**: 保存した目的は継続的に任せる領域。AI が状況を見て「今日はこれを進めたい」と具体的な仕事・理由・対象ファイルを提案し、適用前に相談する。ユーザーがその仕事を明示的に任せると、最新のファイルを読み直して `dailyGoal` の範囲で自走する。個々の可逆操作を再確認しない。その仕事が終われば翌日まで待ち、継続的な委任は保持する。見送った日には実行せず、翌日の相談に進む。
- **automatic**: 合意した目的と範囲内で、仕事の選択から実行まで進める。目的達成時に自動継続を停止する。

提案には、自分で見つけた改善案も理由とともに含める。相談待ちは画面に表示し、音声が既に接続中なら現在の会話へ知らせる。自発的な通知のためにマイクや音声接続を勝手に開始しない。日付が変わった古い提案は実行許可として使わない。

## 実行経路

音声・文字の相談 → 共有設定案 → `AutonomyPanel` で明示確定 → Tauri `autonomy` → 目的・対象・許可に応じた実行経路 → 必要なら今日の仕事の相談 → 結果と検証の報告。

文書の直接操作では、CLI は判断のための専用プロセスであり、ユーザーの通常のターミナルを操作しない。Claude Code の非対話モードで、組み込み tool・MCP・hooks・skills・Chrome・プロジェクト設定を無効化する。stream の初期化情報も検査し、構造化出力以外の tool を受け付けない。Claude Code の既存ログインを使用する。認証情報を再保存しない。

この経路はインストール済み CLI を信頼する transport であり、OS sandbox ではない。既知の管理設定が有効な環境は拒否する。モデルの自己申告を実行許可にせず、外部送信・shell・他の MCP tool を worker に提供しない。

## 実行経路の自動選択

新しい設定は内部の `auto` 経路を使用する。ユーザーには仕事の種類やCLIを選ばせない。目的と許可をもとに実行側が必要な仕事を選ぶ。対象がコミット済みブランチのあるGitリポジトリの正確なルートであり、作成・編集、移動、退避をすべて許可している場合、Codexが独立コピー内で文書やコードを変更し、hostが指定された検証コマンドを再実行する。サブフォルダの指定を親リポジトリ全体の権限へ広げない。検証時点のGitツリーから確認用の成果物を別の場所に書き出し、履歴にはその保存先を表示する。実行用コピーは診断用に残す。元の作業フォルダへ自動反映しない。コピーの起点はコミット済みの内容であり、元フォルダの未コミット変更は引き継がない。

通常フォルダや一部操作だけを許可した範囲は従来の文書操作経路を使う。保存済みの旧文書スコープは、そのままコード実行権限にはならない。ユーザーが統合された説明を確認して設定を保存し直すまで、旧範囲を維持する。MCPや相談モデルは実行経路を選んだり、外部公開を許可したりしない。

隔離コピーで変更を準備するCLIには限定したファイルシステム権限を設定し、この段階ではツールからのネットワーク・commit・公開を無効化する。モデルへの推論リクエストと認証は必要になる。目的達成に必要な後続操作は、下記の汎用実行担当へ渡す。元の資料・コードを壊さずに成果を持ち帰ることを優先する。

## 目的達成に必要な操作の自動許可（2026-10-26）

ユーザーは「目的達成に必要な操作を自動で許可する」を明示的に保存できる。`automaticActionApproval` は既定falseで、旧 `publishPullRequest` の値から引き継がない。commit・push・PR専用の許可ではなく、保存した目的を果たすための具体的な操作への許可であり、必要な外部送信や公開も含む。宛先や内容が不明な場合は質問する。作成・編集／移動／退避の許可がそろわない範囲では、従来の限定文書操作を維持する。

自動許可が有効な場合、検証済みの成果と目的を独立した判断担当が照合する。開発担当が次の操作を返さなくても、納品や公開など目的に必要な操作が残っていれば具体化し、汎用実行担当へ引き継ぐ。変更準備と検証だけで目的達成と扱わない。判断はClaude Code、ツールの実行はCodexを使用し、開発前に判断担当の利用可能性を確認する。自動許可が無効な開発は従来どおりCodexのみで準備でき、具体的な後続操作を個別に確認する。

自動許可は保存した目的・対象フォルダ・ローカル操作・進め方に結び付ける。目的や設定を変更した場合、古い自動許可による待機操作を実行しない。通常会話からの提案や過去の成果物の確認を、自動許可に昇格させない。操作と外部通信の要否を固定して実行前に再検査し、結果と自動許可の履歴を残す。失敗や応答不明の場合は自動継続を止め、同じ外部操作を繰り返さない。CLI本体の既存の拒否設定を解除する権限にはならない。

## 自動起動

アプリ起動中の host poll が期限到来を確認する。保存された契約がなければ起動しない。起動前に作業 ID を耐久保存し、同時に一つだけ実行する。期限を過ぎて起動した場合も一回にまとめ、未処理の回数分を連続実行しない。

実行頻度は5〜1440分。直近24時間の実行上限は1以上の整数で指定でき、48回に制限しない。画面・保存処理・AI相談で正確に受け渡すため、JavaScriptの安全な整数の範囲（最大9,007,199,254,740,991）まで受け付ける。上限に単発実行も含める。アプリ終了中の daemon 実行は実装しない。WebView の timer が抑制された場合は次の tick で遅延実行するため、正確な時刻の実行を保証しない。再起動時に前回の実行中記録があれば、自動再実行せず停止して復旧を案内する。

TS は表示と起動トリガーを所有する。契約の最終検査、実行 claim、キャンセル、変更適用の直列化は Rust の同一境界で扱う。通常の UI 方針を Rust に移すものではなく、権限確認と file mutation の競合を防ぐための限定した責務である。

## 復元

既存の `history` は Yorishiro の pack/config/init 用。この機能は別の `~/.yorishiro/autonomy/changes` に変更前後の内容と復元台帳を保存する。保存完了前にはファイルを変更しない。復元点は自動削除しない。

パスの逸脱、symlink/hardlink、通常文書以外、許可外の操作を拒否する。読み取り後のユーザー編集と、AI の変更後に行われた編集の両方を検査する。競合時にユーザーの新しい内容を上書きしない。元に戻す操作は自動作業を止めた状態で行う。

直接編集経路の対象は `.txt` / `.md` / `.markdown` / `.rst` / `.csv` / `.tsv` / `.log`。隠しファイル、設定、`AGENTS.md`、`CLAUDE.md`、実行ファイルは除外する。読み取りは最大64ファイル・合計256KiBで、除外した対象があることを worker に伝える。フォルダ作成、コード実行、任意 shell、外部送信は含めない。

## 作業後の確認

送信・公開・インストールなど、継続的な自動作業の許可に含まれない操作は、種類に依存しない確認事項として扱う。YorishiroはPR作成やメール送信の実行機能を持たず、具体的な操作に対するユーザーの判断を記録する。GitHubの利用は前提にしない。

確認事項は `pendingActions` に保存し、毎日の仕事を始める前の `pendingWork` と区別する。操作名、対象、影響、具体的内容、確認が必要な理由、元の作業フォルダと成果物を表示する。「承認する」は表示された要求IDと内容のdigestに対する判断であり、古い表示や二重クリックには適用しない。音声の相づちや設定のOnを承認とみなさない。

文書作業のPlanと隔離コピーのReportは、共通の `requestedAction` を返せる。確認のためだけの依頼は、変更ファイルやGitHub remoteがなくても成立する。過去の結果から確認事項を作る場合、足りない宛先や操作を推測して補わず、具体化できない理由を伝える。確認待ちと承認後の引き継ぎ待ちの間は、同じ作業を繰り返さないよう自動実行を止める。作業終了・確認カードの追加・判断の変更はnative eventで画面へ即時通知する。進行中の古い読み取り結果が返った場合は再取得し、15秒ポーリングは通知欠落時の回復用として残す。

新しい作業で確認が必要になった場合、workerは具体的な内容を構造化して返し、hostが「承認待ち」に直接表示する。ユーザーが履歴から確認内容を作成する中間操作は設けない。宛先や内容が未確定なら質問と停止理由を返し、承認カードを推測で作らない。過去の結果を具体化する読み取り専用の準備処理は内部経路として残す。隔離コピーの結果では、保存された元フォルダと基準コミットを読み取り、成果物全体のGitツリーハッシュと検証時の記録を照合してから、変更前後の全文を確認処理へ渡す。要約のみから適用内容を推測しない。読み取りは上限付きで、リンク・改変・バイナリ・上限超過などは理由を表示する。確認用の読み取り中にリポジトリや成果物へ書き込まない。

会話のAIは `autonomy_request_action` で確認カードを提案し、`autonomy_action_context` で画面上の判断を参照できる。MCPから承認・見送りを書き込むことはできない。承認は実行完了ではなく、CLI本体の拒否設定を解除する権限でもない。内容のdigestは表示した確認事項を固定するもので、参照先ファイルの内容を固定するものではない。実行担当は実際の送信・適用内容を再確認し、表示した内容と異なる場合は新しい確認を求める。現在の背景workerは任意の操作を一時停止して再開する仕組みを持たないため、承認結果を参照できることと、実行側に接続されていることを混同しない。実行手段がない場合は未実行と明示する。

承認を取り消しても、他の実行手段ですでに行われた操作は元に戻らない。以前のPR専用試作版の確認事項は、そのまま公開権限として再利用せず、改めて具体的な確認を必要とする。成果物と既存の履歴は残す。

音声接続中は確認待ちを知らせ、未接続なら次のユーザー操作による接続まで待つ。通知のためにマイクを起動せず、通知の受領を発話や承認と扱わない。

## 既存判断との関係

ユーザーは2026-10-24に、可逆な作業について「自分で考えて動き、結果を持ってくる」方向への変更を依頼した。この決定は [loop-presence-layer.md](loop-presence-layer.md) の「Yorishiro は実行を所有しない」という既定方針を、明示的に委任された専用 worker の範囲で更新する。既存 loop 観測経路はそのまま利用できる。[critical-constraints.md](critical-constraints.md) の PTY observation-only と、persona/pack に任意実行権限を渡さない境界は維持する。

## 次の段階

プロバイダーの操作単位の承認要求と再開の接続、複数の役割・目的とフォルダ、アプリ終了中の継続は別工程。確認機能自体にPRやメールなどの実行処理を追加しない。隔離コピーから元の作業フォルダへの統合も自動化しない。

## 目的と判断を中心にした画面整理（2026-10-26）

画面の入口では「何を任せているか」「いま何をしているか」「自分の判断が必要か」を先に確認できる構成にする。設定項目を減らすために、成果物や実行条件、承認の根拠を削除しない。

- 保存済みの目的・対象フォルダ・自動許可の状態を作業状況と一緒に表示する。編集中の設定案は保存済みの委任と区別し、チェックボックスを変更しただけで実行権限が変わったように表示しない。
- 次の判断が必要な仕事と操作を作業履歴より先に示す。送信先・対象・影響は承認前に確認できる状態を保ち、長い操作内容や成果物・検証結果は開いて確認できる。承認ボタンと見送りボタンを会話上の返答に置き換えない。
- 頻度、上限、ローカル操作、CLIの実行条件などの詳細設定と、ファイル一覧・ブランチ・成果物の保存先・テスト結果などの証拠は段階的に開示する。進行状況だけでなく、失敗理由や未実施の操作を追えるようにする。
- 自動許可は既定で無効とし、選択肢の近くに外部送信・公開が都度の確認なしで進むことを示す。AIの判断違いで情報が送信されたり外部に変更が残ったりする可能性があり、停止しても完了済みの外部操作は元に戻らない。保存された許可の状態を通常画面からも確認できるようにする。現在の実行はアプリ起動中に限られ、クラウド上で常時動作するような説明はしない。
- 固定ラベル、操作説明、状態表示、日時、アクセシブルな名前をアプリの日本語・英語設定に合わせる。ユーザーの目的、既存の実行報告、ファイル名、コマンド、検証結果は原文を保持し、翻訳済みのUIと区別する。開閉する領域はキーボードで操作でき、閉じた詳細へフォーカスが移らず、承認待ちへの案内とダイアログを閉じた後のフォーカス復帰を維持する。

参考にしたMetaの[How We Designed Muse](https://introducing.muse.ai/)は、短い作業状況から活動履歴や許可へ進む構成、目標の追跡、明確な承認・拒否操作を説明している。[How We Built Safety Into Muse](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)は、会話とは別のクライアントUIで具体的な操作の許可を扱う境界を説明している。ここでは目的・状況の見やすさと判断の明確さを設計上の参考にし、Museの実行環境や権限保証をYorishiroが持つとは扱わない。

## 2026-10-25 UIとセキュリティの確認

[Linearの設定](https://linear.app/docs/account-preferences)と[Raycastの設定](https://manual.raycast.com/settings)の実際の画面を参照し、項目のまとまり・見出し・状態表示を整理した。デスクトップでは相談と設定欄を並べ、ヘッダーに閉じるアイコンを配置する。入口は上部ツールバーの画面共有ボタンの隣に置き、On/Off・実行中の状態と承認待ち件数を表示する。アイコンを押す操作はパネルを開くだけで、開始や承認は行わない。右下の重複した入口は設けない。保存済みの設定は折りたたみ、現在の状態と自動作業On/Off、実行中の停止、未承認の操作を上部に表示する。承認履歴は折りたたみ、作業履歴は最新3件の短い要約を初期表示する。全件表示と詳細の展開で元の記録を参照できる。見出しは「AIに相談」「任せる範囲」「作業履歴」のような機能名にする。「つながっています」のような比喩や、読点で区切るコピー調の見出しを避ける。設定を保存して有効にする説明は「この範囲で任せる」ボタンに直接結びつける。

音声相談の相手であるキャラクターの表情を残すため、背景全体のぼかしを外し、薄い暗幕と不透明なパネルで読みやすさを確保する。背景のターミナルへの操作はモーダルで遮断する。

独立レビューで、専用CLI設定にすると個人の禁止・確認ルールが抜ける問題を確認した。Codexの対応可能な宣言的なprefix_ruleからprompt/forbiddenだけを引き継ぎ、許可による権限拡張は持ち込まない。hostが再実行する検証コマンドもnative execpolicyで検査し、要確認・禁止なら実行しない。未対応の動的ルール、読み取り専用設定、独自の権限プロファイル等は黙って無視せず停止する。[公式設定仕様](https://learn.chatgpt.com/docs/config-file/config-basic)が説明する設定の優先順位を踏まえ、専用設定に分離するだけで元の制限を引き継げるとは扱わない。

ClaudeのBash等の拒否は、対応するツールを与えない文書処理では構造的に満たす。hostによる文書読み書きがファイル制限を迂回しないよう、対象フォルダと祖先の制限を読み取り前・変更直前に検査する。元のCLIの実行フックを持ち込むものではなく、全プロバイダーの設定を相互変換する完全な互換層でもない。

当初の実装は停止時にプロセスグループを終了させていたが、切り離された子プロセスが残る場合を実機で再現した。検証済みGitオブジェクトから、実行プロセスに書き込み権限のない別フォルダへ確認用成果物を保存することで、完了後の書き換えを防ぐ。内容ハッシュ、パス、リンク、ファイル数・容量を検査し、既存成果物を上書きしない。すべての子プロセスや資源消費の停止を保証するものではない。

追加修正では、プロセスグループだけの終了を実行単位の監視へ置き換える。ランダムな継承マーカーと観測済みの親子関係から子プロセスを追跡し、macOSのaudit tokenを使ってPIDの再利用による無関係なプロセスの終了を避ける。正常終了・キャンセル・タイムアウト・出力超過のどの場合も、観測したプロセスの終了を確認してから処理枠を解放する。列挙や終了確認に失敗した場合は停止完了とせず、理由を表示して次の作業を待たせる。通常のターミナル操作は対象にしない。

これは任意の悪意あるプログラムを完全に封じ込める仕組みではない。観測前にマーカーを消して親子関係からも離れたプロセスは検出を逃れる可能性があり、その保証にはVM等の別の隔離方式が必要。確認用成果物の隔離も維持する。今回の監視実装はmacOSのみであり、他OSの自律workerは開始前に未対応エラーとする。Linux向けには別途、PID再利用に耐える終了処理と実機検証が必要。
