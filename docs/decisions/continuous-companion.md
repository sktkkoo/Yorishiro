# 継続する会話と現在の理解

Status: implementation（2026-11-01）

初回起動時はターミナルを表示する。以後はView Modeと同様に、画面を切り替えた時点で選択を設定ファイルへ保存する。お任せ作業画面を開いたまま終了・クラッシュした場合も、次回起動時にその画面へ戻る。タイトルバーの自律実行アイコンからウィンドウを開き、上部のOn／Offスイッチで自律実行を明示的に変更する。目的を設定して作業を開始する旧Auto画面、頻度設定、契約、定期worker、旧MCP操作は撤去する。既存のターミナル、3Dキャラクター、音声接続は維持する。

## 体験

会話・過去の理解・ペルソナをもとに、キャラクターが提案するか待つかを選ぶ。提案数やPR数を増やすことは目的にしない。初対面で共有した過去を創作せず、既存の経験がある場合は出典を持って引き継ぐ。日本語の標準キャラクター名も `Yori` とする。

ユーザーの発言は先に保存し、モデルの返答・草案・理解の更新は実際の完了結果から表示する。画面を閉じることと処理の寿命を分ける。モデルが利用できない場合はエラーを表示し、サンプル返答で代用しない。

「いまの理解」には、好み・背景・任された範囲・仮説を表示する。各項目の「そう理解した経緯」から、根拠の会話、以前の理解、関連する振り返りを開く。日記を別タブにしない。訂正は会話として記録し、古い解釈と出典を残して更新する。

## 実行と記録

`continuity` がpersona単位の会話・理解・経緯・草案を永続化する。画面はnativeイベントとsnapshotを購読する。画面を開いた時、新しい会話・草案への反応、処理の完了をきっかけにモデルが判断する。

自律実行がOnのときだけ、画面を開いた際の再考・定期的な検討・次の一手の自動実行を行う。画面を開閉してもOn／Offを変更しない。各処理の結果は、ユーザーへ伝える返答と、すぐ実行できる具体的な次の一手（`nextStep`）を別々に持つ。次の一手があれば完了直後に進み、30分の周期を待たない。草案を進めるだけなら発言は空でもよい。提案や作業の必要がなければ次の一手を空にして黙って待ち、5分後に再確認する。「何もありません」という通知は出さない。

Onのpersonaでは、native側が次の処理と5分ごとの再確認を所有する。画面を閉じる・ウィンドウを非表示にする・ターミナルへ切り替える操作でも継続する。開始済みの状態と作業文脈を保存し、再起動後の文脈同期で再開する。別のpersonaへ切り替えた場合は以前のpersonaの新規自動処理を止め、受理済みの処理は完了させる。Offのpersonaでは文脈同期だけで自律作業を開始しない。テスト期間中の新規personaとOn／Off未保存の旧データはOnを初期値とし、ユーザーが明示的に保存したOffは再起動後も維持する。Offに切り替えると未送信の自動処理と次の一手を停止し、その時点で実行中の受理済み作業は結果を回収してから止める。Offのまま再起動した場合、未回収の依頼は保持し、再びOnにするか明示的に再試行するまで復旧処理を開始しない。手動の会話や草案操作は引き続き利用できる。フォーカス復帰だけで新しい検討を増やさない。

次の一手は完了した状態のrevisionと現在の文脈が一致する場合だけ受理し、進行中の処理へ重ねない。重複した手順、同じ返答、振り返りや時刻だけの更新では連続処理を継続しない。次の処理からさらに続けるには、実際の草案やユーザーの発言に根拠を持つ理解が進んでいる必要がある。単なる提案の言い換えや自分の発言を根拠にした記憶の書き換えを進展と扱わない。失敗した会話・訂正は保持して5分後に再試行する。会話や草案へのユーザーの入力は待機中でもすぐ反映する。

継続する作業とユーザーへの通知を分ける方針は、[Museの設計記事](https://introducing.muse.ai/)も参考にした。5分の待機時間はYorishiro側の選択である。画面表示中だけ動く旧条件は継続稼働の要件に合わせて撤去した。

同じpersonaの保存を複数プロセスから上書きしないよう、会話を保持する間はOSの排他ロックを持つ。別のYorishiroで同じpersonaを開いている場合はエラーと再試行を表示する。先のアプリが終了するとロックは解放され、再試行で最新の保存状態を読む。日本語・英語の標準Yoriは同じ記憶とロックを共有し、別のpersonaは独立する。

CodexのMain Agentが利用できる場合、お任せ作業はその選択中の会話へ通常の作業ターンとして渡す。既存の依頼と任された範囲から次の具体的な一手を選び、調査・編集・検証を実行して結果を戻す。音声の返答や新たな開始指示を待つことを前提にしない。モデル・作業フォルダ・sandbox・承認設定は上書きせず、承認要求は既存のターミナルで扱う。Main AgentのセッションID・選択中の会話・作業フォルダを照合し、別のタブやsubagentへ送らない。

開始前に作業IDと対象会話を保存し、送信直前にも送信試行を記録する。再試行は同じ作業IDを会話履歴から探して結果を回収する。送信済みか不明な場合や履歴を読めない場合に、作業を再送しない。新しい音声の書き起こしや画面を閉じる操作で、受理済みの作業を取り消さない。実際のツール完了と新しい成果がある場合は、返答がなくても次の作業へ進む。単なる質問・提案の言い換えを成果と扱わない。

Main Agentが実行中なら開始を延期する。ただしCodexの`turn/start`にはidle状態を条件とする原子的な開始指定がなく、確認直後のターミナル入力・音声からの委譲と合流する可能性がある。その場合はユーザーの作業を優先し、別のユーザー入力を含むターンの成果をお任せの進展として扱わず、自動の次の一手を開始しない。ターミナルへ切り替えた後も、開始済みpersonaの新しい自動作業をnative側から継続する。

Codexの実行経路がない場合は、ツールを持たないClaude CLI transportで返答・解釈・草案を生成する。草案はアプリ内の実データとして保存し、外部での実作業を完了したとは表示しない。Claudeの残高不足・認証・利用制限は、提案形式の失敗と区別して表示する。旧Autoの保存済み契約や自動許可を新機能へ移さない。

Main AgentとGPT Liveの開始時にも現在の理解を渡す。MCPの `continuity_context` で最新の理解と経緯を確認し、`continuity_observe` で実際の会話を記録できる。外部会話はsourceKeyで重複を避ける。観測の受領は学習処理の完了や実行権限の付与を意味しない。

GPT Liveでは確定したユーザーの音声書き起こしを同じ記録へ戻し、理解・会話・草案の更新を接続中の音声へ渡す。更新だけで発話やマイクを開始しない。書き起こしイベントには発話ペアを特定するIDがないため、確定部分をそのまま記録し、対応するAIの返答を推測して補わない。接続・ペルソナが変わった後の古いイベントは採用しない。

新しい音声書き起こしは`voice`出典で保存し、同じ音声接続へ会話の新着として送り返さない。Main Agentなどからの外部観測は引き続き共有する。Codex利用中の観測は記録だけを行い、書き起こし断片ごとに競合する実行ターンを起動しない。理解の更新は次の自律的な判断へまとめる。音声には、一度尋ねたことを無返答時に繰り返さず、任された作業は続け、新しい結果があるときだけ伝える方針を渡す。

旧 `~/.yorishiro/autonomy` の履歴・成果・復元台帳と、既存のjournalは消去しない。旧おまかせを新バージョンで自動再開することもない。

## 継続稼働の検証

各workerの観測を保存状態の`workRuns`に結果と同じ保存単位で残す。依頼ID、開始・終了時刻、実行経路、完了・失敗・終端の区別、実ツールの進展を記録する。回収の再試行は同じ依頼IDを保持し、新規実行数には数えない。revisionの増加やアプリの生存だけを実行回数と扱わない。記録の追加以前の稼働時間・回数は遡って推定しない。

依頼作成時の`createdAt`を保存し、観測には`requestCreatedAt`として引き継ぐ。回収処理の`startedAt`は観測した時刻であり、元の実行開始を証明しない。schemaVersion 2の観測では、元の依頼作成が観測開始後だと確認できるものだけを回数に加える。元の時刻が不明な旧依頼の回収を新規実行として数えない。

schemaVersion 3では、`mainAgent`と`pi`の完了依頼を別々に数える。`uniqueCompletedAutonomousRequests`と24回条件には、そのうち自動呼び出しの`trigger=return`または`followup`で完了した依頼だけを用いる。手動メッセージ、再試行、trigger不明の記録は自律回数に加えない。backend別と`ToolCapable`の集計は従来どおり手動依頼も含み、実ツールの進展数も別に数える。text経路、不明なbackend、失敗、依頼作成時刻を確認できない過去の回収は完了回数に加えない。これらの回数だけで連続稼働や成果品質の達成とは判定しない。稼働中のschemaVersion 2観測は途中で書き換えず、Pi切替後の検証では新しい観測ファイルを開始する。

12時間以上・24回以上の実アプリ稼働、クラッシュ後の結果回収と再開、成果に対するユーザーの95点以上の評価は別々に検証する。単体テストや短時間の観測だけではこれらの達成を主張しない。

読み取り専用の観測CLIを実際のnativeアプリPIDに接続する。標準では12時間、30秒ごとに保存状態とプロセスの生存をJSONLへ記録する。`--output`には新しいファイルを指定する。既存の観測記録は上書きしない。

```sh
python3 -B scripts/observe-continuity-soak.py --pid <native-app-pid> --output /tmp/yorishiro-soak.jsonl --duration-seconds 43260 --live-mcp-url http://127.0.0.1:18743/mcp
python3 -B -m unittest discover -s scripts -p 'test_observe_continuity_soak.py'
```

再起動時にlauncherがPIDファイルを更新する環境では`--pid`の代わりに`--pid-file <path>`を使う。`--executable /absolute/path/to/yorishiro`でも実行ファイルの一致から追跡できる。観測開始より前に始まった依頼は回数に加えない。Main Agentの完了依頼数と実ツールの進展があった依頼数を分け、会話・草案・エラー本文を観測ログへコピーしない。PIDの生存確認はそのプロセスが正しいアプリかを保証せず、観測間の連続性や再起動復帰の正しさ、成果の品質も証明しない。これらには実際の依頼と成果の照合、クラッシュ復帰の試験、ユーザーの評価が必要になる。

`--duration-seconds 43260`は、実測のsample間隔を12時間以上にするための余裕を含む。live MCPのURLは稼働アプリの接続先に合わせる。保存失敗時はディスク上のsnapshotが古い`working`のまま残ることがあるため、稼働中のnative snapshotも読み取り専用で照合する。同じpersonaのphase・revision・エラーの有無だけを記録し、接続失敗やpersona不一致は未確認として残す。差異は取得時刻の差でも起きるため、それだけで停止とは断定しない。観測プロセスが容量不足などで終了した場合、終了後の時間を稼働時間へ加えない。

## pi harnessの評価（2026-11-05）

ユーザーの指定により、Codex / Claude Codeを実行harnessにしない構成も評価する。現行upstreamは[earendil-works/pi](https://github.com/earendil-works/pi)、調査対象commitは`9e870f6f002ca6c21ce010fdb99122afe3738b28`。CLIのRPCと`pi-durable`は別の選択肢として扱う。

| 候補 | 接続と保存 | 今回の評価点 |
| --- | --- | --- |
| pi coding-agent RPC | Rustから長寿命subprocessへJSONLを送る。セッション保存とイベントを利用する | 現行native hostに接続しやすい。コマンド受理と処理完了を分け、`agent_settled`まで購読する。CLIのセッション保存だけで途中のツール操作の再開を保証しない |
| pi-durable | TypeScript側のharnessにSQLite等のstorageを渡す。タスクと依頼IDを永続化する | 保存済みタスク・待機期限の再開、同じrequestIdの重複排除を直接評価できる。実験的APIのためcommit/versionを固定して試す。アプリ側に専用workerと通信経路が必要 |

ユーザーの了承を受け、`pi-durable`の専用workerを組み込む方針で進める。これは12時間・24回や成果品質の達成を示すものではない。自ら候補を探して選ぶ判断、任された範囲、成果の提示と評価はYorishiro側が所有する。CLIのRPCを使うだけでは`pi-durable`の保存・再開機能は得られない。

durable側のschedulerを使っても、失敗後の継続設定とhostの復帰処理は必要になる。`afterFailedRun`の既定は後続入力を待つため、無人稼働では`continue`等の方針を実試験する。cross-process lockはhostが所有し、現在のpersona単位の排他をworker側のstorageにも適用する。既定のrestart limitを消して同じクラッシュを無限再試行することを継続稼働の成功とは扱わない。

実行経路の分岐点は`continuity`のexecutorとする。terminalのagent一覧にpiを足すだけでは、選択中の会話やPTYへの依存が残る。personaと作業フォルダからworkerを解決し、native ownerが起動・復帰を管理する。既に送信を試みた依頼は元のbackendと会話に結び付けて回収し、piへ切り替えて再実行しない。

検証には、実モデルでの調査・編集・実行結果の提示、dispatch前後とツール実行中のプロセス終了、同じ保存状態からの再開、同一requestIdの重複投入、長い待機とAPI障害からの復帰を含める。副作用のあるツールは、依頼の重複排除とは別に実行前後の照合が必要。pi-durableのツールも、途中でプロセスが落ちた場合に安全な再実行を宣言していない操作を無条件で再実行する設計ではない。

`experiments/pi-harness`で実ライブラリとSQLiteを使い、別プロセスへの再openと同一依頼の重複排除、副作用直後に強制終了したunsafe toolの回収を試験する。モデルはupstreamの決定的なテスト用providerであり、実モデルの判断、Yorishiroへの接続、12時間の稼働や成果品質の評価を代替しない。

モデルへの接続と認証はCLIの選択から分ける。既存Codexのsandboxや承認経路はpiへ自動では移らないため、workerに渡すツールと権限、保存先、予算と障害時の再試行をhostが明示する。これらを含む実試験の後に、採用と既存保存状態の移行を判断する。

一次資料：[RPC](https://github.com/earendil-works/pi/blob/9e870f6f002ca6c21ce010fdb99122afe3738b28/packages/coding-agent/docs/rpc.md)、[SDK](https://github.com/earendil-works/pi/blob/9e870f6f002ca6c21ce010fdb99122afe3738b28/packages/coding-agent/docs/sdk.md)、[durable harness](https://github.com/earendil-works/pi/blob/9e870f6f002ca6c21ce010fdb99122afe3738b28/packages/durable/README.md)。

## pi native接続の実装段階

native executorにPi専用のJSONL接続経路を追加する。保存した実行対象は`{backend, target}`で識別し、backendのない旧形式だけをCodexとして読む。明示された不明なbackendは旧形式へフォールバックしない。送信を試みた依頼は現在の画面の選択より先に元のbackendから回収する。

Piの実行対象はworkspace、persona、保存先、Nodeとworkerの絶対パス、provider、model、明示的なツール権限に結び付ける。`~/.yorishiro/continuity/pi-worker.json`には`nodePath`、`workerEntry`、`provider`、`model`、`permissions: {read, write, commands}`を設定する。資格情報を実行対象へ複写しない。権限のない旧Pi対象は読み取れるが本番workerを起動しない。未設定なら起動前に明示的に失敗し、Codex、Claude、fixtureへ切り替えない。

本番entryと設定・権限制御は`runtime/pi-worker`に実装する。認証方式は`authMode`で指定し、API-key方式は選択したproviderの環境変数だけを使う。OAuth方式はopenaiとPi専用の絶対パス`authPath`を明示し、API-key方式へ自動代替しない。native実行とオフライン診断は同じ解析で方式・参照先を渡し、workerのreadyでも照合する。保存するのは方式とファイル参照だけで、資格情報の内容を複写しない。旧Targetの方式省略はAPI-key方式として読み、既存CLIの資格情報やOAuthへ自動移行しない。ファイルの読み書きはcanonical workspace内に制限し、コマンドはhostが固定したprogram/argvをcommandIdで選ぶ。これはOS sandboxではなく、許可したコマンドは利用者のOS権限で動作する。詳細と制約は[runtime README](../../runtime/pi-worker/README.md)に記す。

実Pi/SQLiteとテスト専用modelを使い、作成・編集・固定コマンドによる検証・再起動後の同一依頼回収を試験する。実モデルの認証成功、製品UIからの選択、runtimeの配布、実アプリの切替と12時間・24回・95点の達成は未確認のまま区別する。

プロトコルv2のreadyでprovider/model/保存先/workspace/権限と本番・fixtureの区別を検証する。再開ではdurable requestIdの受領記録を先に照会し、未確認の送信を再送しない。stdout/stderrは継続して消費し、観測timeoutだけで生きたworkerを再起動しない。終了処理はこのhostが所有するChildだけを対象にする。新しいPi workerは同じSQLite内のUUID epochとroot IDをadmission契約として返す。hostは初回送信のmessage/schema/target/契約をprivate outboxへ永続化してからdispatchを記録する。受領記録が無い回収は、その保存payloadとDB epoch/root/実行対象が一致するときだけ同じ依頼IDでPiの重複排除付き受領へ進める。記録のない旧PiやCodex依頼にはこの再送を適用しない。プロセス中断の復旧と、DBの巻戻し・電源断・外部副作用のexactly-onceは区別する。

## 後回しにするもの
