# いつもの続き — 継続する住人の体験プロトタイプ

Status: HTML interaction prototype / 本体への実装前の設計検討（2026-10-31）

依頼を入力して仕事を始める画面から、よりと過ごしてきたことが次の判断につながる画面へ。会話・背景での取り組み・振り返りを一つの経験として扱う。ユーザーが目的を書くことを入口の条件にしない。

前の [おまかせ作業デモ](../omakase/index.html) を残して、別案として作成した。本体のターミナル、Auto workspace、実行権限、実データは変更していない。

## 開く

[index.html](index.html) をブラウザーで開く。外部サービスへの接続は不要。

キャラクターは前のデモに生成済みの `../omakase/character.bundle.js` を共用する。ない場合だけリポジトリのルートで次を実行する。

```sh
node prototypes/omakase/build-character.mjs
```

バンドルはローカルのVRMとモーションを含むgitignore対象のファイル。公開・再配布しない。読込に失敗しても会話とノートは操作できる。

## 今回合意した方向

- 会話から好み、その理由や背景、任されている範囲を継続的に理解する。背景での取り組みからも経験を得る。
- ペルソナは、何を気にかけるか、どの案を選ぶか、どう切り出すかに控えめに影響する。
- 個別の取り組みが終わっても、関係・記憶・関心は続く。仕事全体の開始／停止／再開を主導線にしない。
- 新しいことをする価値がないときは静かに過ごせる。何もしていない時間にも架空の作業状態を付けない。
- 専用画面で一連の体験を先に検証する。ターミナルにも自然に接続することは必要だが、今回ターミナルの構成は変えない。
- 起動時の既定画面をどちらにするかは未決定。HTMLで体験を確認してから本体の設計を進める。

## 一つの体験として試す

1. **よりから始まる。** 昨日の「細かいPRが増えて全体が見えない」というサンプル会話を覚えていて、いくつかの変更に共通する問題を見つけたと話す。ユーザーが新しい目的を設定する手順はない。
2. **会話で見方が変わる。** 「PRをまとめるより、体験から考えてほしい」と返す。よりは当初の解釈を改め、何を大切にするかを更新する。仕事の結果だけで好みを断定しない。
3. **話している間にも進む。** 変更をまとめる案から、使い始めの体験を描く草案へ進む。会話欄は引き続き使える。作業の結果は会話に紐づく成果として届く。
4. **経験が残る。** 「いまの理解」に、好み・背景・任された範囲をまとめる。各項目の「そう理解した経緯」を開くと、根拠の会話、以前の理解、そのときの振り返りを確認できる。「訂正する」で会話から更新できる。
5. **翌日に効く。** 外枠の「翌日を試す」で時間を進める。修正した理解に沿った声のかけ方になる。「提案は少なめがいい」と伝えた場合は、その距離感も引き継ぐ。

外枠の「体験を切り替える」から、過去の共有経験がない初対面、静かに過ごす場面も試せる。切替はこのプロトタイプの状態をリセットする操作。会話中の「今は話すだけ」「見送る」は、その取り組みを引っ込めることであり、住人全体を終了する操作ではない。

## 画面の役割

左のキャラクターと短い状態表示、中央の続いていく会話、必要なときに開く「いまの理解」で構成する。成果物はその話が出た位置に置く。作業一覧、目的設定、実行頻度の設定を入口に並べない。

記憶と日記のタブは設けない。通常は現在の理解だけを見せ、出典や変化は項目ごとの「そう理解した経緯」に折りたたむ。振り返りは同じ会話IDを持つものだけを結び付ける。古い保存に会話IDがない場合は保存された引用と日付を使い、同日や空のIDを根拠に関連を推測しない。保存済みの会話・記憶・振り返りは引き継ぐ。

ペルソナの違いは口調だけでなく、出来事の受け止め方に現れる。この試作では「切れ切れのままになっていることが気になる」というよりの着眼点を、小さな言葉と案の選択に置く。人格の違いを示すために行動範囲を広げることはしない。

## 本体のための設計案

以下は実装済みの仕様ではなく、この体験から検討する構造。

### 続くものと、一区切りになるもの

| 続くもの | 内容 |
| --- | --- |
| 経験 | 会話、実際に観測した変化、作業結果、ユーザーの反応。出典と時点を残す |
| ユーザーへの理解 | 好み、理由、背景、任された範囲。事実と仮説を区別し、訂正で更新する |
| 気にかけていること | 未解決の問題、取り組む理由、過去に見送った理由、見直すきっかけ |
| ペルソナ | 着眼点や選び方の傾向。経験による理解と一緒に判断へ渡す |
| 個別の取り組み | 調査・草案・実装・統合など。その都度の検証可能な完了条件を持つ |

内部で取り組みの目的や完了条件を持つことと、人間に毎回それを設定させることを分ける。前者は成果の質と継続性のために必要。後者を主導線から外す。

### 判断の循環

会話や状況の変化を受け取る → 関係する経験を思い出す → 理解を更新する → 未完了の取り組みと照合する → 進める・提案する・待つを選ぶ → 実際の結果を確かめる → 次の判断に残す。

新しい情報・ユーザーの反応・既存の取り組みの変化を再考のきっかけにする。常時接続を、常時推論や毎回のファイル変更と同一視しない。イベントをまとめ、状況に応じて待ち時間と資源上限を設ける。

既存の未完了PRや草案を先に照合し、同じ問題について別の作業を作り続けない。PR作成後も、任された範囲で競合・CI・統合状態を追う。検証済みの作業結果は経験の証拠になり、好みの証拠にはユーザーの発言や反応を使う。

振り返りは、経験から何を受け止め、どんな理解が変わったかを残す。画面では現在の理解に結び付く経緯として読む。振り返りの文章そのものを実行権限の根拠にせず、実行の根拠と結果は追える状態を保つ。

### AIが一度に読む量

1回の判断で読み込む記憶・経緯にtoken数の上限を設ける案とする。履歴の保存は継続する。「いまの理解」は短く保ち、判断に関係する項目を優先する。根拠の確認や矛盾の解消に必要な場合に、対応する会話・振り返りを追加で取得する。

任された範囲、禁止事項、進行中の判断に関わる直近の訂正は優先枠として確保する。履歴を追加取得する場合も、1回の判断全体の上限を超えない。必要な根拠が不足する場合は未確認として扱い、任された範囲を推測で広げない。現在の会話・ペルソナ・出力用の枠も別途確保し、具体的な上限は判断の質、応答時間、費用を評価して決める。このHTMLではAI接続やtoken制御は実装しない。

### 今の実装から使えるもの

- persona の `thinking.systemPromptAddition` と、Main Agent／音声への注入。
- persona ごとの journal と `memories.md`。現状は起動時に選んだ記憶を主に使うので、継続更新は設計が必要。
- 既存の自律worker、検証された成果物、具体的操作の実行記録。
- 作業結果を会話へ戻す `work_status_context`。

現在の自律workerは目的・ファイル・直近の作業履歴を主な入力にしており、personaと関係の記憶を共通して参照する経路はない。画面の変更に続いて、会話と背景作業から同じ理解を更新する経路を作る必要がある。

参照：[auto-workspace](../../docs/decisions/auto-workspace.md)、[自律作業](../../docs/decisions/autonomous-document-work.md)、[journalの注入](../../src/core/global-prompt/journal-fragment.ts)、[自律worker](../../src-tauri/src/autonomy/mod.rs)。

## この試作で検証すること

- 何も依頼していない段階で、キャラクターから自然に会話が始まったと感じるか。
- 提案が以前の会話とつながっている理由を理解できるか。
- 訂正によって、後の提案や行動が実際に変わったと分かるか。
- 進行中にも会話でき、見送っても関係が途切れないか。
- 現在の理解から、その根拠と変化をたどれ、次の判断へのつながりが分かるか。
- 性格が少し見え、役に立つことと静かに過ごすことが両立するか。

PR数や提案数を成功の基準にしない。まず一連の体験の納得感、訂正の伝わり方、余計な介入の少なさを見る。本体では成果の採用、未完了の放置や重複、人間が後始末した量も検証する。

## デモの範囲

会話と分岐は端末内のスクリプト。LLM、GPT Live、マイク、GitHub、本体のjournal、ファイル変更には接続していない。会話・作業・日付の経過はサンプルであり、実際のプロジェクト調査や翌日の実行を表さない。自由入力は限られた分岐を試すためのもので、未知の内容を理解・学習したとは扱わない。

このページ用の `localStorage` に体験の状態を保存する。記憶の更新はモデルの学習ではなく、用意した状態遷移。音声や身体との同期を検証する試作でもない。
