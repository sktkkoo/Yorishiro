# おまかせ作業の体験デモ

HTMLで体験を固めてからYorishiro本体へ反映する。現時点では本体のコード、GPT Live、実行エージェントには接続していない。

## 設計の軸

ユーザーが決めるのは、何を任せるかと結果をどうするか。会話の設定や進行管理をユーザーの仕事にしない。

Yorishiroでは、よりが会話の相手になり、隣の資料が仕事の対象になる。話すためのフォームを操作するのではなく、会話から依頼が形になり、その場所で成果になる。VRMは会話の状態を伝える。仕事の状態は資料側に一度だけ表示する。

この原則から、次の判断をした。

- 通常は「話しながら」。開始後は会話を続けられる。発話ごとの送信、読み上げチェック、音声入力の設定は設けない。
- 声を出さないときは「静かに」へ切り替える。会話と音声を終え、文字欄を出す。仕事、入力途中の文章、作成中の依頼、成果は引き継ぐ。切り替えで作業権限は変えない。
- 会話の終了と仕事の停止を分ける。会話が終わっても仕事は続き、止める対象は仕事そのもの。
- 作業対象は現在のワークスペースを引き継ぐ。対象が変わるときだけフォルダ名から変更する。
- 成果物には保存、変更案には反映と見送りを置く。操作の結果は動詞と具体的な対象で伝える。
- 一回の依頼から成果を受け取る流れに絞る。定期実行、頻度、通知などの詳細設定はこの主導線に持ち込まない。

説明を減らすために、必要な情報まで隠さない。実際の会話、成果物の内容、変更対象、回復に必要なエラーは残す。仕組みや試作の制約は製品の主導線から分離する。

## 二つの使い方

| | 話しながら | 静かに |
|---|---|---|
| 入口 | よりの下の「話しかける」 | 依頼欄 |
| 伝え方 | 続けて会話 | 文章を送る |
| 返事 | 声と最新の発話 | 画面とやりとり |
| 操作 | ミュート・会話終了 | 入力・送信 |
| 仕事と成果 | 共通 | 共通 |

「話しながら」へ切り替えただけでは会話を開始しない。開始操作が必要。画面非表示や終了後にも自動で再開しない。

## 今回取り除いたもの

「音声は文字にして確認できます」「途中で相談や追加の指示もできます」などの説明、読み上げチェック、文字起こしから手動送信するフロー、進捗の重複、重複した保存ボタン、完了直後の定期実行設定を削除した。

ナビゲーション用サイドバーは置かない。作業履歴は上部から開く。キャラクター領域は本体の通常表示と同じ幅280px。画角35°と `defaultCameraForCharacter` によるカメラ位置を利用する。

## 会話デモの範囲

本体の「話しかける」は、Codex選択時に既存のGPT Liveへ接続する音声対話を想定する。HTMLでは固定の会話を試す。

- 「話しかける」で開始し、右下の「発話サンプル」から会話を進める。
- 「今週のメモをまとめて」→よりの質問→「うん、それもお願い」で依頼が形になり、仕事が始まる。
- 作業中に進捗を尋ねたり、止めたり、成果を短くまとめ直したりできる。
- 会話中の割り込み、ミュート、終了、モード変更、画面非表示では古い返答を破棄する。
- `conversation.js` はマイク、音声認識、ネットワークを使わない。端末内の日本語音声があれば返事を読み上げ、なければ字幕と時間経過で再現する。
- 声・キャラの口・全身モーションの同期は未実装。聞く・考える・話す・作業するの姿勢と視線を試す。
- 作業は約11秒のサンプル。反映・公開・復元もデモ内の状態変更だけ。実ファイルは変更しない。

「体験デモ · GPT Live未接続」を外枠に表示し、詳しい制約はそこから開ける。発話サンプルの操作部分は本体への移植対象ではない。

## 開く

生成済みの `character.bundle.js` があれば `index.html` をChromeで直接開ける。現在のワークスペースには生成済み。

HTTPで開く場合はリポジトリのルートから実行する。

```sh
python3 -m http.server 4173 --bind 127.0.0.1
```

`http://127.0.0.1:4173/prototypes/omakase/` を開く。

VRM表示の再生成には既存依存と `public/models/Yori.vrm`、`public/animations/Idle.vrma` を使う。

```sh
node prototypes/omakase/build-character.mjs
```

生成ファイルは約30MBでgitignore対象。ライセンス付きモデルとモーションを含むためローカル確認専用。公開・再配布しない。元アセットは変更しない。

## 確かめたいこと

- 説明を読まずに、話しかけてから成果を受け取れるか。
- 会話を終えても仕事が続くと理解できるか。
- 「静かに」への切り替えで作業を引き継げるか。
- よりと資料のどちらを見るか、自然に注意が移るか。

検証では初回の迷い、完了までの操作数、結果の理解、会話と仕事の停止の取り違えを記録する。説明文の追加より先に、入口・配置・状態遷移を見直す。

## 本体に反映するとき

会話デモを既存のGPT Liveへ、描画をThreeRuntime / character-surfaceへ接続する。文字と声の依頼が同じ仕事を更新し、入力方法を切り替えても目的・対象・履歴が分断されないことが前提。

マイク接続や発話完了は作業開始の承認として扱わない。デモの会話順序をそのまま実行制御へ移植せず、会話状態と作業状態を分ける。承認が必要な操作は具体的な対象と結果に結び付け、既存の権限・停止・復元・競合保護を維持する。

本体は現在、単一の継続契約・順次実行・アプリ起動中のみ。複数仕事や予約実行は別の要件として扱う。

参照：[音声対話](../../docs/decisions/codex-realtime-voice.md)、[自律作業](../../docs/decisions/autonomous-document-work.md)、[キャラクター表示](../../src/character-surface.tsx)。Meta Museからは、会話を継続しながら依頼することと、具体的な成果に対して判断することを参考にした。

## 今回の確認

- 会話アダプターの53項目、画面と状態遷移の41項目をスタブ / jsdomで確認。古い応答の破棄、モード間の下書き共有、会話終了後の作業継続、停止・再開、反映・見送り・復元を含む。
- Chromeで実VRM、会話による相談から成果への遷移、「静かに」への切り替えを確認。
- JavaScript構文とローカルVRMバンドル生成を確認。GPT Liveの接続品質、実マイクによる会話、音声と口形の同期はこのHTMLの検証対象外。
